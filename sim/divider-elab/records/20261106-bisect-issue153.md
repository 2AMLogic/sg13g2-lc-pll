# divider speed deck operating-point bisect (issue #153), 2026-11-06

Why `sim/divider-elab/divider_speed.spice.tmpl` cannot get an operating point at the current `design/netlist/divider.spice`.
Simulated, **nominal corner only** (`hbt_typ` / `mos_tt` / `cap_typ`, 27 C, 3.3 V), ngspice-46 (host; pin says 47, mismatch warned by
`lib-ngpin.sh`), `psp103_nqs.osdi` loaded via `pre_osdi` (#152 is merged at the base commit `725ca89`). Not measured.
Method: the speed deck rendered with the same `sed` substitutions as `scripts/run-divider-elab.sh`, then `tran` replaced by `op` for
the variants; one local `ngspice -b` at a time, `OMP_NUM_THREADS=2`, `timeout 40` per variant. "hang" = the 40 s cap hit while ngspice
was in gmin/source stepping after "The temperature limiting function received NaN"; none of the hung runs ever printed an operating point.
These were one-off scratch decks (not committed).

## Reproduction

Unmodified speed deck, 120 s cap: `The temperature limiting function received NaN`, dynamic gmin stepping failed, true gmin stepping
started and never finished. Same symptom as the issue report; `Unknown model type` count 0 (the NQS load works).

## Bisect (op only)

| variant | op |
|---|---|
| full deck (2 dividers on `iref` + 2 ideal-clock counter chains) | hang |
| minus both ideal-clock counter chains (2 dividers only) | **converges**, `iref` = 0.882 V |
| minus one divider (either one) | hang |
| counter chains only (no dividers) | converges |
| minus counter chain 4 / minus counter chain 3 | hang / hang |
| minus both `acounter` instances (keep `mcounter` + FB flop) | hang |
| minus both FB flops (`dff_tg_hv`) | **converges** |
| minus both `mcounter` instances | **converges** |
| full deck + `.nodeset` on the `cml2cmos` bias nodes (values from the converged 2-divider run) | hang |
| full deck + the above + `.nodeset` on all 471 counter nodes (values from the converged counters-only run) | hang |
| full deck + `.option noopiter` / `itl1=1000` / `gminsteps=0 srcsteps=100` / `method=gear` | hang (each) |
| full deck, `tran ... uic` with `.ic` on the bias nodes | op skipped; transient starts but advances ~4.5 ns in 110 s |

## Finding

- The self-biased `cml2cmos` (the `c8fdb58` / `bc16d94` change) is **not by itself** the cause: two dividers on a shared `iref` converge
  (as `divider_elab` / `divider_tran` already show), and a nodeset on its bias nodes does not rescue the full deck.
- The failure needs the dividers **and** the `mcounter` + FB-flop pair of the ideal-clock control chains in one circuit; remove either
  and the op converges. Neither half is unsolvable alone, so this is a DC-solver path problem on the combined latch-heavy circuit
  (NaN in the HBT temperature-limiting function while gmin stepping), not a missing initial condition on one node. Nodeset, solver
  options and `uic` did not give an op-converged, practical run.
- Separate cost problem: the dividers-only deck simulated 10 ns in 97 s, i.e. about 25 min for the 150 ns the check needs, and the
  counters-only deck did not finish 10 ns in 100 s. A split deck would converge but is not cheap on this one-core host.

## Outcome (acceptance criterion (b))

The speed check **cannot run in its current single-deck form**; `scripts/run-divider-elab.sh` stops at the speed step. No deck or
script change is made here. The workable direction (not implemented, not run end to end) is to split the check into a dividers-only
deck and a counters-only control deck and merge their `wrdata` for `scripts/divider_speed_counts.py`; that needs a wiring change in
`scripts/run-divider-elab.sh` and an accepted run time, so it is filed as its own issue. `design/` and `design/netlist/divider.spice`
are untouched.

Side observation: `design/netlist.sh --check divider` also reports STALE on this host because `klt netlist` emits an extra
`** klt-netlist-inputs: {...}` header line that the committed netlist does not carry; `run-divider-elab.sh` therefore stops at its
staleness gate before the speed step is even reached.
